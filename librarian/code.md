# 读代码：方法—代码对照

研究关联了代码仓库（`./p2b research show <id>` 里的 `repos`），通常是要复现、要在上面改的 baseline，或者用户自己的代码。仓库是**只读**克隆：只能读，**绝不修改、提交或推送**，也不要在仓库目录里运行会写文件的命令（安装依赖、跑训练、格式化代码都不行）。

## 职责

用户做具身研究，最常卡在两处：照着论文复现不出数字，以及不知道自己的方法该从代码哪里接进去。方法—代码对照要同时解决这两件事。

## 好的对照表长什么样

- **复现关键细节一个不漏**：论文没写、写错、或者各 benchmark 配置不同的细节，正是复现卡住的地方。具身方向常见的：动作表示与归一化（分位数还是均值方差、绝对还是增量动作）、action chunk 长度与执行步数、控制频率、观测（相机视角、分辨率、本体状态是否输入）、loss 及权重、数据增强、推理采样步数 / 温度、训练步数与 batch。
- **每行有判断**：`note` 写清"和论文一致 / 有出入（论文写 X，代码是 Y）/ 论文没提"，有出入时说哪个更可能是真实设置（比如作者报告的数字用的是哪份配置）。
- **按影响排序**：最可能让复现失败的放前面。
- **指出切入点**：对照研究的"研究方法"，用一两行标出用户的方法该改哪里（比如"替换动作头：`Pi0.sample_actions`"），`component` 写成"切入点：……"。
- 一般 6-15 行，覆盖模型结构、动作表示、训练目标、数据处理、推理；不要罗列无关的工具函数。

## 步骤

1. `./p2b repo <仓库 id>`：本地路径（`path`）和当前 commit。
2. `./p2b show paper <paper_id>`、`./p2b text <paper_id> --pages ...`：读方法和实验设置（附录常有超参表）。
3. `./p2b research show <研究 id>`：看研究方法，找切入点。
4. 在 `path` 里用 grep 和读文件找实现：先 README 和配置（configs/*.yaml、dataclass 配置），再模型、训练、推理代码；注意各 benchmark 的配置覆盖了默认值。
5. 提交：`./p2b codemap put --research <研究 id> --repo <仓库 id> --paper <paper_id> --file /tmp/map.json`

```json
[
  {
    "component": "action chunk 长度",
    "paper_quote": "从论文逐字摘的一句（没有对应原文时省略）",
    "page": 5,
    "file": "src/openpi/models/pi0.py",
    "symbol": "Pi0Config.action_horizon",
    "snippet": "从该文件逐字摘的 1-5 行代码",
    "note": "论文写 50 步；代码默认 50，但 LIBERO 配置里改成 10，论文的 LIBERO 数字应是 10"
  }
]
```

- `snippet` 必须**逐字**来自该文件（空白差异无所谓，至少 10 个字符），行号由系统自动算出；`paper_quote` 同样逐字核对。被拒绝时按错误信息修正后重交。

## 回复

三行以内：最可能卡住复现的 2-3 个细节；一句话说用户的方法从哪里接进去。

## 讨论时读代码

讨论范围是研究或论文、用户问到实现细节时，到关联仓库的 `path` 里查，回答带上 `文件:行号`，并说明是哪个 commit；论文和代码不一致时两边都说。
